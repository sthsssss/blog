공유 메모리는 블록 안의 스레드들이 데이터를 교환할 수 있는 온칩 저장 공간입니다. 블록이 한 SM에 배치된다는 규칙과 함께 이해해야 합니다. 프로그램은 이 공간에 어떤 값을 저장하고 언제 다른 스레드가 읽을지 직접 결정합니다.

배열 덧셈에서는 스레드끼리 값을 교환할 필요가 없었습니다. 이번에는 배열의 합을 구한다고 가정합니다. 여러 스레드가 읽은 값을 하나의 결과로 결합해야 하므로 협력과 동기화가 필요합니다.

## 서로의 입력을 읽기 전에 기다려야 한다

257개 원소를 블록 크기 128로 나눕니다. 각 스레드가 원소 하나를 공유 메모리에 기록한 뒤, 블록의 스레드 0이 그 값을 합산합니다. 이 코드는 공유와 배리어의 동작을 보여 주는 기준 예제이지 빠른 병렬 reduction 구현은 아닙니다.

```cpp
__global__ void BlockSum(const float* input, float* partial,
                         unsigned int count)
{
    __shared__ float values[128];
    unsigned int local = threadIdx.x;
    unsigned int index = blockIdx.x * 128 + local;

    values[local] = index < count ? input[index] : 0.0f;
    __syncthreads();

    if (local == 0)
    {
        float sum = 0.0f;
        for (unsigned int i = 0; i < 128; ++i)
        {
            sum += values[i];
        }
        partial[blockIdx.x] = sum;
    }
}
```

실행 계약은 블록당 정확히 128개 스레드와 블록 수만큼의 출력 공간입니다. `values`는 각 블록에 따로 존재합니다. 블록 0과 블록 1이 같은 공유 배열을 놓고 경쟁하는 구조가 아닙니다.

입력이 모두 1이면 결과는 `[128, 128, 1]`입니다. 이것은 전체 합 257이 아니라 블록별 부분 합입니다. 전체 합을 얻으려면 이 세 값을 후속 단계에서 결합해야 합니다.

## 배리어가 보장하는 범위

`__syncthreads()`는 블록의 스레드들이 협력하는 배리어입니다. 이 지점 이전에 다른 스레드가 수행한 관련 메모리 접근이 이후 접근에서 올바르게 관찰되도록 하며, 스레드들의 진행을 맞춥니다. 배리어 없이 스레드 0이 읽기 시작하면 다른 스레드가 아직 값을 기록하지 않았을 수 있습니다.

마지막 블록에서도 범위 밖 스레드는 0을 기록하고 배리어에 참여합니다. 입력 범위 검사 안에 배리어를 넣어 일부 스레드만 도달하게 만들면 올바른 블록 동기화 구조가 아닙니다. 블록 전체가 같은 조건을 따르는 경우와 레인마다 조건이 다른 경우를 구분해야 합니다.

배리어는 그리드 전체를 기다리지 않습니다. 다른 블록의 부분 합까지 준비되었다고 가정할 수 없습니다. 일반적인 해결은 부분 합 커널과 후속 커널을 같은 스트림에 순서대로 제출하는 것입니다. 특별한 cooperative launch를 사용하는 전역 동기화는 자원과 실행 조건이 별도로 필요합니다.

## fence와 atomic은 배리어가 아니다

메모리 fence는 메모리 연산의 순서를 제한하는 수단이며, 다른 스레드가 특정 지점에 도착할 때까지 기다리는 수단과 같지 않습니다. atomic은 해당 연산의 원자성을 제공하지만, 모든 참여자가 계산을 끝냈다는 증명은 아닙니다. 메모리 순서와 범위도 사용한 연산의 계약에 따라 확인해야 합니다.

따라서 “메모리 문제가 있으니 atomic을 쓰자”로 해결책을 정하지 않습니다. 충돌하는 갱신을 원자적으로 만들려는지, 생산 완료를 기다리려는지, 앞선 쓰기의 관찰 순서를 보장하려는지부터 구분합니다. NVIDIA의 [동기화 함수 설명](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-c-programming-guide/index.html#synchronization-functions)과 [메모리 fence 설명](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-c-programming-guide/index.html#memory-fence-functions)은 이 책임을 나누어 정의합니다.

## 공유 메모리도 주소 패턴의 영향을 받는다

공유 메모리는 여러 뱅크로 구성됩니다. 여러 레인이 서로 다른 주소를 동시에 접근할 때 그 주소들이 같은 뱅크에 몰리면 요청이 나뉘어 처리될 수 있습니다. 같은 주소의 broadcast와 서로 다른 주소의 뱅크 충돌은 구분해야 합니다. 구체적인 처리 방식은 세대와 접근 폭에 따라 달라집니다.

행렬 전치 같은 작업에서 배열 차원에 padding을 추가하는 이유는 이 주소 배치를 바꾸기 위해서입니다. 단순히 배열을 크게 만드는 것이 아니라 동시에 접근하는 레인들의 뱅크 대응을 바꾸는 것입니다.

## 부분 합에서 타일 재사용으로

행렬 곱에서는 입력 조각 하나가 여러 출력 계산에 반복 사용됩니다. 블록이 필요한 입력 타일을 공유 메모리로 가져온 뒤 여러 스레드가 재사용하면 장치 메모리에서 같은 값을 반복해서 읽는 양을 줄일 수 있습니다.

하지만 타일이 크면 공유 메모리와 레지스터 사용이 늘고 상주 블록 수가 줄어들 수 있습니다. 배리어 비용도 생깁니다. 재사용으로 줄어드는 데이터 이동량과 자원 점유가 늘어나는 비용을 함께 고려해야 합니다.

공유 메모리는 이제 “빠른 메모리”가 아니라 특정 협력 패턴을 구현하는 자원으로 이해할 수 있습니다. 다음 문서에서는 이 패턴이 행렬 곱과 Tensor Core의 사용으로 어떻게 확장되는지 설명합니다.
