GPU 애플리케이션의 아키텍처는 빠른 커널 하나로 완성되지 않습니다. 입력을 받아 계산하고 결과를 반환하는 동안 코드·가중치·버퍼·스트림을 얼마나 오래 유지하는지, 여러 요청이 어떤 자원을 공유하는지 결정해야 합니다. 장치가 여러 개가 되면 데이터의 위치와 통신도 다시 설계해야 합니다.

앞 문서까지의 단일 GPU 모델을 유지하면서 경계를 하나씩 넓히겠습니다. 새로운 기능은 기존 구조를 대체하는 용어 목록이 아니라 어느 비용이나 제약을 바꾸는지로 설명할 수 있습니다.

## 초기화와 요청 처리의 분리

매 요청마다 장치를 초기화하고 가중치를 전송하고 버퍼를 할당하면 계산 시간 외의 비용이 반복됩니다. 변하지 않는 모델과 장치 코드는 오래 유지하고, 요청마다 바뀌는 입력과 출력만 교체하는 구조를 고려할 수 있습니다.

```text
프로세스 시작
  → 장치·코드 준비
  → 모델과 지속 버퍼 준비

요청 처리
  → 사용 가능한 작업 버퍼 확보
  → 입력 전송·커널·결과 전송
  → 완료 확인
  → 결과 반환·버퍼 재사용

프로세스 종료
  → 진행 중인 요청 완료 또는 실패 처리
  → 장치 자원 정리
```

이 구조에서 버퍼 풀은 단순한 메모리 재사용 장치가 아닙니다. 아직 GPU가 사용하는 버퍼를 다른 요청에 주지 않는 수명 관리 장치입니다. 요청의 지연 시간과 전체 처리량도 구분해야 합니다. 더 큰 배치가 처리량을 높이더라도 입력을 모으는 대기 시간이 늘 수 있습니다.

CUDA Graph는 반복되는 작업과 의존 관계를 그래프로 구성하여 재사용하는 기능입니다. 작은 작업을 자주 제출하는 비용을 줄이는 후보가 되지만, 입력 이동이나 실제 연산량을 자동으로 없애지는 않습니다. 그래프의 노드와 의존성은 스트림에서 설명한 실행 계약 위에 있습니다. [CUDA Graph 설명](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-c-programming-guide/index.html#cuda-graphs)은 생성·인스턴스화·실행 단계를 구분합니다.

## 세대의 변화는 어느 제약을 바꾸었는가

G80의 계산 경로에서 시작한 CUDA는 같은 기본 실행 모델을 유지하면서 하드웨어 기능을 확장했습니다. 연도를 암기하기보다 변화가 어느 계층에 있는지 구분하는 편이 유용합니다.

| 변화의 예 | 바뀌는 대상 | 프로그램에서의 의미 |
| --- | --- | --- |
| Fermi의 계산 기능 강화 | 캐시, 배정밀도, ECC 등 | 더 다양한 접근·정밀도·신뢰성 요구에 대응 |
| Pascal의 제품별 구성 차이 | SM, 메모리, 연결 기능 | 같은 세대 이름만으로 성능·기능을 확정할 수 없음 |
| Volta의 Tensor Core와 독립 스레드 스케줄링 | 행렬 실행 유닛, 진행 상태 관리 | 새 연산 경로와 동기화 주의점 |
| Ampere의 비동기 데이터 이동 기능 | 전역→공유 메모리 준비 경로 | 계산과 데이터 준비를 겹치는 설계 |
| Hopper의 TMA와 블록 클러스터 | 데이터 이동과 협력 범위 | 더 큰 타일·협력 실행의 새로운 표현 |

NVIDIA의 [Fermi 백서](https://www.nvidia.com/content/pdf/fermi_white_papers/nvidiafermicomputearchitecturewhitepaper.pdf), [Ampere 튜닝 가이드](https://docs.nvidia.com/cuda/archive/12.6.0/ampere-tuning-guide/index.html), [Hopper 튜닝 가이드](https://docs.nvidia.com/cuda/archive/12.6.0/hopper-tuning-guide/index.html)는 각 변화가 요구하는 조건을 설명합니다. 모든 제품이 그 세대의 모든 기능을 갖는 것은 아닙니다.

Hopper의 블록 클러스터는 일반적인 블록 단위 협력보다 넓은 범위의 협력을 제공합니다. 이를 이유로 이전 장치의 모든 블록이 서로 공유 메모리를 읽을 수 있다고 해석하면 안 됩니다. 기본 모델과 조건부 확장을 분리해야 호환성과 최적화의 범위를 판단할 수 있습니다.

## 장치가 두 개가 되면 메모리도 두 개가 된다

두 GPU에 배열 덧셈을 나누는 것은 출력 구간을 분할하는 비교적 단순한 작업입니다. 하지만 행렬이나 모델을 나누면 한 장치가 만든 중간 결과를 다른 장치가 필요로 할 수 있습니다. 연산을 나눈 만큼 통신이 생기므로 GPU 수만큼 빨라진다고 가정할 수 없습니다.

PCIe와 NVLink 같은 연결은 데이터 이동 경로입니다. 지원 여부와 대역폭은 제품·보드·서버 구성에 따라 다릅니다. peer access가 가능한지도 확인해야 하며, 여러 GPU를 장착했다고 메모리가 자동으로 하나의 빠른 배열이 되지는 않습니다.

여러 서버까지 확장하면 네트워크 인터페이스와 전송 경로가 추가됩니다. GPUDirect RDMA는 지원되는 구성에서 GPU 메모리와 I/O 장치 사이의 데이터 경로를 개선하는 기술입니다. 메모리 등록, 토폴로지와 완료 순서의 문제까지 사라지는 것은 아닙니다. [NVIDIA의 GPUDirect RDMA 문서](https://docs.nvidia.com/cuda/gpudirect-rdma/index.html)는 관련 경계를 설명합니다.

## NCCL은 통신 라이브러리다

여러 GPU가 각자 계산한 값을 합쳐 모든 장치에서 사용하려면 AllReduce 같은 집합 통신이 필요합니다. NCCL은 이러한 GPU 간 통신 연산을 제공하는 라이브러리입니다. 단일 SM의 명령 스케줄러도, 애플리케이션의 전체 분산 실행 프레임워크도 아닙니다.

[NCCL 개요](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/overview.html)는 장치 간 통신과 토폴로지에 대한 역할을 설명합니다. 애플리케이션은 어떤 데이터를 언제 교환할지 결정하고, 통신 연산을 계산과 올바르게 연결해야 합니다. 통신을 겹치더라도 소비자가 필요로 하는 데이터의 완료 조건은 남습니다.

## 여러 사용자가 하나의 GPU를 사용할 때

여러 프로세스가 같은 GPU를 사용하는 문제는 한 프로세스가 여러 스트림을 사용하는 문제와 다릅니다. 컨텍스트, 스케줄링, 메모리 용량과 격리 요구를 고려해야 합니다.

MPS는 CUDA 다중 프로세스의 협력적인 실행을 지원하는 서비스입니다. MIG는 지원되는 GPU에서 계산·메모리 자원을 인스턴스로 분할하는 기능입니다. 둘은 동일한 격리 모델이 아니며, 지원 기능과 보장 범위를 제품·버전별로 확인해야 합니다. 각각 [MPS 문서](https://docs.nvidia.com/deploy/mps/index.html)와 [MIG 사용자 가이드](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/introduction.html)에 관리 단위가 설명되어 있습니다.

보안·장애 격리와 처리량을 같은 지표로 취급하지 않습니다. 독립된 사용자 작업을 운영할 때에는 자원 제한, 실패 복구, 지연 시간 변동과 관측 가능성도 설계 요구입니다. 이 기능들은 GTX 1070 예제의 실행 검증 범위에는 포함되지 않습니다.

## 하나의 구조로 설명하기

이제 배열 덧셈의 경로를 처음부터 끝까지 연결할 수 있습니다. CPU 프로세스가 입력을 준비하고, 컴파일된 장치 코드와 실행 상태를 사용해 작업을 제출합니다. 블록은 SM에 배치되고 워프의 명령은 실행 유닛과 메모리 계층을 사용합니다. 스트림과 이벤트는 순서와 완료를 연결하며, 호스트는 필요한 완료 이후 결과를 사용합니다.

느린 경우에는 이 경로에서 어느 자원이 제한되는지 찾습니다. 새로운 GPU나 라이브러리를 도입할 때에는 어느 구간을 바꾸는지 확인합니다. 여러 장치와 사용자로 확장할 때에는 데이터의 위치와 공유·격리 경계를 추가합니다.

이 모델이 있으면 새로운 기능을 만날 때도 이름부터 외울 필요가 없습니다. 코드 생성, 실행 상태, 데이터 이동, 동기화, 자원 관리 중 어느 책임에 속하는지 먼저 놓고 기존 구조와 연결할 수 있습니다.
