GPU 계산의 성능은 커널 실행 시간만으로 결정되지 않습니다. 장치 초기화, 코드 준비, 메모리 할당, 입력 전송 및 결과 대기에도 시간이 필요합니다. 반복 실행에서는 이 비용 중 어느 부분을 매번 수행하고 어느 부분을 재사용하는지에 따라 결과가 달라집니다.

이 문서에서는 계산을 초기화·반복 실행·종료 단계로 나누고, 측정하려는 구간에 맞는 시계를 선택하는 방법을 설명합니다.

## 반복 실행에서 유지할 자원

선형 계층에 여러 입력을 적용한다고 가정합니다. 모델의 가중치가 바뀌지 않는다면 매 입력마다 가중치를 장치로 복사할 필요가 없습니다. 최대 입력 크기와 출력 크기가 정해져 있다면 작업 버퍼도 재사용할 수 있습니다.

```text
초기화
  장치 선택 → 실행 준비 → 가중치 전송 → 작업 버퍼 할당

반복 실행
  입력 전송 → 선형 계층 → 활성화 → 선형 계층 → 결과 사용

종료
  진행 중인 작업 완료 확인 → 버퍼·스트림 등 정리
```

CUDA Runtime API는 컨텍스트와 모듈 관리의 일부를 자동으로 처리합니다. 따라서 애플리케이션 코드에 명시적인 모듈 적재가 없어도 첫 실행에 준비 비용이 포함될 수 있습니다. Driver API를 사용하면 이러한 자원을 더 직접적으로 관리할 수 있습니다.

버퍼를 재사용하려면 이전 작업이 해당 버퍼의 사용을 끝냈는지 확인해야 합니다. 한 스트림에서는 순서로 표현할 수 있고, 여러 스트림에서는 이벤트 등으로 의존성을 연결할 수 있습니다. 재사용은 할당 횟수만 줄이는 작업이 아니라 수명과 실행 순서를 설계하는 작업입니다.

## 측정할 질문 선택

성능 수치를 기록하기 전에 무엇을 알고 싶은지 정해야 합니다.

| 측정 대상 | 포함하는 작업 | 판단할 내용 |
| --- | --- | --- |
| 첫 실행 시간 | 초기화와 코드 준비를 포함한 첫 요청 | 시작 시 사용자 대기 시간 |
| 커널 구간 | 지정한 GPU 작업 구간 | 계산 구현의 변화 |
| 전체 지연 | 입력 준비·전송·실행·결과 사용까지 | 애플리케이션의 응답 시간 |
| 처리량 | 일정 시간에 완료한 입력 수 | 반복 처리나 배치 처리 능력 |

커널이 빨라졌어도 전체 지연은 거의 변하지 않을 수 있습니다. 입력이 작고 전송이나 제출 비용이 대부분인 경우가 대표적입니다. 반대로 여러 요청을 묶으면 처리량이 증가하더라도 개별 요청의 대기 시간이 늘 수 있습니다.

## CUDA 이벤트로 구간 측정

CUDA 이벤트는 스트림의 진행 지점을 기록할 수 있습니다. 다음 코드는 한 스트림에서 반복한 커널 구간의 시간을 측정합니다.

```cpp
Check(cudaEventRecord(start, stream));

for (unsigned int i = 0; i < iterations; ++i)
{
    FillPattern<<<gridSize, blockSize, 0, stream>>>(
        deviceOutput, count);
    Check(cudaGetLastError());
}

Check(cudaEventRecord(stop, stream));
Check(cudaEventSynchronize(stop));

float milliseconds = 0.0f;
Check(cudaEventElapsedTime(&milliseconds, start, stop));
```

시작 이벤트와 종료 이벤트를 같은 스트림에 기록합니다. 종료 이벤트가 완료된 뒤 경과 시간을 읽으면 두 이벤트 사이의 장치 시간 구간을 얻습니다. 반복 횟수로 나누면 이 실행 조건에서 반복당 평균 구간을 계산할 수 있습니다.

이 값에는 두 이벤트 사이에서 발생한 장치의 대기나 작업 간 빈 구간이 포함될 수 있습니다. 아주 짧은 커널에서는 호스트의 제출 속도도 연속 실행에 영향을 줄 수 있습니다. 이벤트 측정값을 언제나 순수 산술 명령의 시간이라고 해석하지 마세요.

NVIDIA Runtime API의 [이벤트 관리 문서](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__EVENT.html)는 이벤트 기록과 경과 시간 계산의 조건을 설명합니다.

## 호스트 시계로 전체 시간 측정

애플리케이션의 전체 지연에는 `std::chrono::steady_clock` 같은 호스트 시계를 사용할 수 있습니다. 다만 비동기 커널을 제출한 직후 시계를 멈추면 완료 시간이 아니라 제출 시간에 가까운 값을 측정합니다.

결과 복사와 필요한 완료 대기까지 측정 구간에 포함해야 합니다. 측정 시작 전에 이전 요청이 남아 있으면 그 작업의 대기까지 포함될 수 있으므로 시작 상태도 정해야 합니다.

이벤트 시간과 호스트 시간은 서로 다른 질문에 답합니다. 수치가 다르다고 어느 하나가 잘못된 것은 아닙니다. 어떤 작업이 각 구간에 포함되는지 기록하면 차이를 설명할 수 있습니다.

## 재현 가능한 비교

첫 실행에는 초기 준비와 캐시 상태의 영향이 있습니다. 안정 상태의 반복 성능이 필요하면 준비 실행을 수행한 뒤 여러 표본을 수집합니다. 첫 요청의 지연이 중요한 제품이라면 준비 실행으로 그 비용을 숨기지 말고 별도로 보고합니다.

GPU 이름, 드라이버, 도구 버전, 입력 크기, 블록 크기 및 측정 구간을 함께 기록하세요. 그래픽 작업 등 같은 GPU를 사용하는 다른 부하도 결과에 영향을 줄 수 있습니다. 평균만으로 변동을 숨기지 않도록 여러 표본과 중앙값 등을 함께 확인할 수 있습니다.

점유율은 SM이 수용할 수 있는 최대 워프 수에 대한 상주 활성 워프 수의 비율입니다. 높은 점유율은 대기 시간을 숨길 여지를 제공할 수 있지만 높은 성능 자체를 뜻하지는 않습니다. 레지스터를 줄이려고 메모리 접근이 늘어나면 점유율이 높아져도 느려질 수 있습니다.

## 플랫폼의 이식성과 성능

첫 문서에서 CUDA는 하드웨어와 개발 환경을 함께 제공하는 플랫폼으로 등장했습니다. PTX와 실행 모델은 GPU 세대 사이에서 프로그램을 연결하지만, 특정 입력에서의 성능까지 고정하지는 않습니다.

GPU 아키텍처, 라이브러리 및 컴파일러가 바뀌면 같은 알고리즘의 유리한 배치도 바뀔 수 있습니다. 직접 작성한 기준 커널과 라이브러리 구현을 같은 수치 조건에서 비교하면 새로운 기능이 어느 구간에 도움이 되는지 확인할 수 있습니다.

이 시리즈의 예제는 실행과 검증의 기준을 제공합니다. 실제 애플리케이션에 적용할 때에는 먼저 수치 결과를 확인하고, 병목 구간을 측정한 뒤, 변경 하나씩 효과를 비교하세요. 빌드와 실행 방법은 다음 검증 부록에서 확인할 수 있습니다.
