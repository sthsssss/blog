SIMT(Single Instruction, Multiple Threads)는 여러 스레드에 공통 명령을 적용하면서 각 스레드의 상태를 유지하는 실행 모델입니다. CUDA 프로그램은 스레드 하나의 동작을 작성하고, GPU는 워프에 속한 스레드들의 명령을 함께 처리합니다.

같은 명령을 처리한다는 말은 값이 모두 같다는 뜻이 아닙니다. 각 스레드는 자신의 인덱스와 계산 값을 가집니다. 조건식도 스레드별로 평가되므로 같은 워프 안에서 실행할 경로가 달라질 수 있습니다.

## 같은 계산과 서로 다른 값

앞의 패턴 커널에서 한 워프의 첫 두 스레드를 고려해 보세요.

```cpp
output[index] = 3 * index + 7;
```

인덱스 0인 스레드는 7을 계산하고, 인덱스 1인 스레드는 10을 계산합니다. 적용하는 연산은 같지만 피연산자와 기록할 주소가 다릅니다. 각 스레드의 변수는 소스에 한 번만 선언되어 있어도 스레드별 값으로 취급됩니다.

이 모델은 많은 정점이나 픽셀에 비슷한 처리를 적용하던 GPU의 작업 형태와 연결됩니다. 다만 CUDA의 스레드는 픽셀을 의미하지 않습니다. 프로그램은 그 실행 인스턴스를 배열 원소, 행렬의 행 또는 다른 계산 단위에 대응시킬 수 있습니다.

## 워프 안에서 조건이 달라지는 경우

원소 257개를 처리하는 마지막 블록에서는 첫 스레드의 전역 인덱스가 256입니다. 이어지는 스레드의 인덱스는 257, 258처럼 증가합니다.

```cpp
if (index < count)
{
    output[index] = 3 * index + 7;
}
```

마지막 블록의 첫 워프에서 인덱스 256만 조건을 만족합니다. 나머지 레인은 배열 기록에 참여하지 않습니다. GPU는 어떤 레인이 해당 명령에 참여하는지 구분하여 처리합니다.

두 개의 긴 경로를 가진 조건문에서는 다른 결과가 나타날 수 있습니다. 같은 워프의 일부 스레드는 참 경로를 실행하고 다른 스레드는 거짓 경로를 실행해야 한다면, 두 경로를 각각 필요한 레인에 적용하는 실행이 필요합니다. 이와 같은 워프 내 경로 분리를 분기 발산이라고 합니다.

짧은 조건문은 컴파일러가 명령별 조건 실행으로 바꿀 수도 있습니다. 따라서 소스에 `if`가 있다는 사실만으로 실제 분기 명령이나 일정한 비용을 단정할 수는 없습니다. 변환 방식과 무관하게 필요한 레인에만 결과를 적용해야 한다는 의미는 유지됩니다.

## 경계 검사와 불규칙한 작업 구분

배열 끝의 경계 검사는 전체 작업 중 일부에만 영향을 줍니다. 원소 수가 충분히 크다면 대부분의 워프가 모든 레인으로 같은 계산을 수행합니다. 배열 밖 쓰기를 막기 위한 검사를 제거하는 것은 이러한 작은 실행 차이의 해결책이 아닙니다.

반면 스레드마다 반복 횟수가 크게 다른 알고리즘에서는 영향이 넓어질 수 있습니다. 예를 들어 한 워프의 스레드 대부분은 반복을 두 번 수행하지만 한 스레드는 수백 번 수행한다면, 남은 계산 동안 참여하지 않는 레인이 생깁니다.

이 경우에는 서로 비슷한 작업을 같은 워프에 배치하거나 작업 분배 방식을 바꾸는 방법을 검토할 수 있습니다. 하지만 재배치에도 비용이 있으며 데이터 순서를 바꾸면 다른 메모리 접근에 영향을 줄 수 있습니다. 변경 전후를 같은 입력으로 측정해야 합니다.

NVIDIA의 [분기와 발산 지침](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/#branching-and-divergence)은 워프 내 경로 차이를 성능 판단의 대상으로 설명합니다. 이 지침은 모든 분기를 제거하라는 규칙이 아닙니다.

## 실행 모델과 동기화 계약

같은 워프에 속한다고 해서 스레드 사이의 데이터 교환을 동기화 없이 작성해도 되는 것은 아닙니다. 메모리에 값을 기록한 뒤 다른 스레드가 읽어야 한다면 필요한 순서와 가시성을 보장해야 합니다.

Volta는 스레드별 실행 상태를 더 세밀하게 관리하는 독립 스레드 스케줄링을 도입했습니다. NVIDIA의 [Volta 튜닝 문서](https://docs.nvidia.com/cuda/volta-tuning-guide/index.html#independent-thread-scheduling)는 이전의 암묵적인 워프 동시 진행에 의존하던 코드가 명시적 동기화를 필요로 할 수 있음을 설명합니다.

따라서 워프는 성능과 실행 구조를 이해하는 단위이고, 동기화 함수는 스레드 간 순서를 표현하는 계약입니다. 두 개념을 대신 사용할 수는 없습니다. 블록 전체가 데이터를 교환하는 예제는 공유 메모리와 배리어 문서에서 다룹니다.

지금까지 스레드별 계산 상태를 설명했습니다. 다음 문서에서는 그 상태와 배열이 실제로 어떤 메모리 공간에 놓이는지 살펴봅니다.
