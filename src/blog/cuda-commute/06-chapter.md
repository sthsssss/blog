GPU 메모리를 설명할 때에는 누가 접근할 수 있는지, 얼마나 오래 존재하는지, 실제 어디에 저장되는지를 구분해야 합니다. CUDA의 global·local·shared라는 이름은 이 세 질문에 모두 같은 방식으로 답하지 않습니다. 특히 local memory는 스레드 전용이라는 의미이지 반드시 SM 안의 빠른 저장 공간이라는 의미가 아닙니다.

배열 덧셈에서는 입력과 출력이 장치 버퍼에 있고, 각 스레드는 입력값을 읽어 중간값을 계산합니다. 같은 함수 안에 등장하더라도 배열 원소와 중간값은 서로 다른 저장 경로를 사용할 수 있습니다.

## 주소는 위치 그 자체가 아니다

호스트 프로그램이 받는 장치 포인터는 장치 메모리를 지칭하는 주소입니다. 가상 주소와 물리 메모리가 다르다는 CPU의 모델은 여기에서도 중요합니다. 포인터의 숫자가 같아 보인다고 CPU와 GPU가 같은 방식으로 그 주소를 접근할 수 있다는 뜻은 아닙니다.

통합 가상 주소 지정(UVA)은 지원되는 환경에서 호스트와 장치 메모리를 하나의 주소 체계로 구분할 수 있게 합니다. 이것은 모든 메모리가 자동으로 이동하거나 모든 포인터를 양쪽에서 역참조할 수 있다는 보장이 아닙니다. 주소 식별과 접근 가능성, 물리적인 데이터 이동은 별개의 문제입니다.

예제의 `cudaMalloc` 버퍼는 장치 측 저장 공간으로 사용합니다. 호스트는 `cudaMemcpyAsync`로 데이터를 옮깁니다. 이 단순한 경로에서는 데이터의 위치와 이동 시점을 코드에서 명시적으로 확인할 수 있습니다.

## 프로그램의 공간과 물리적 계층

| 이름 | 프로그램에서의 범위 | 일반적인 저장·접근 경로 |
| --- | --- | --- |
| 레지스터 | 스레드의 피연산자·중간값 | SM의 레지스터 파일 |
| local memory | 스레드 전용 주소 가능 저장 | 장치 메모리와 캐시 경로 |
| shared memory | 블록 내 스레드가 공유 | SM의 온칩 저장 공간 |
| global memory | 장치의 여러 스레드가 접근 | L1 사용 정책·L2·장치 DRAM |
| constant memory | 커널에서 읽기 전용인 특정 공간 | 상수 캐시 경로 |

이 표는 저장 장치 목록과 완전히 같은 표가 아닙니다. 예를 들어 global memory의 값이 L2에 캐시될 수 있어도 프로그램의 주소 공간이 shared memory로 바뀌지는 않습니다. 일부 GPU에서는 L1과 공유 메모리가 온칩 용량을 나눠 쓰지만, 캐시와 소프트웨어 관리 저장 공간이라는 책임은 여전히 다릅니다.

상수 메모리도 “작은 데이터이면 무조건 빠르다”는 규칙이 아닙니다. 워프의 여러 스레드가 같은 주소를 읽는 패턴과 각기 다른 주소를 읽는 패턴은 다르게 처리될 수 있습니다. 텍스처 접근은 별도의 캐싱·주소 지정 기능을 제공하지만, 모든 일반 배열 접근의 기본 경로는 아닙니다.

## 지역 변수가 레지스터라는 보장은 없다

소스의 `float value`는 언어 수준의 변수입니다. 컴파일러는 값을 없애거나, 레지스터에 두거나, 주소가 필요한 저장 공간을 사용할 수 있습니다. 레지스터 요구가 많으면 일부 값을 local memory로 보내는 spill이 발생할 수도 있습니다.

```cpp
float value = a[i];
c[i] = value + b[i];
```

이 코드만 보고 정확히 몇 개의 물리 레지스터를 사용하는지 알 수는 없습니다. 주소 계산, 루프 상태와 컴파일러 변환도 자원을 사용합니다. PTX의 가상 레지스터 선언만 세는 것도 충분하지 않습니다. 최종 코드 생성 단계의 자원 보고를 확인해야 합니다.

레지스터 사용량을 줄이면 상주 워프 수가 늘 수 있지만, spill로 메모리 접근이 증가하면 오히려 느려질 수 있습니다. 자원 사용을 하나의 숫자로 최적화하지 않고 실행 결과와 함께 비교해야 하는 이유입니다.

## 공유 메모리가 캐시와 다른 이유

캐시는 하드웨어가 주소와 정책에 따라 데이터를 보관합니다. 공유 메모리는 프로그램이 무엇을 언제 넣고 어느 스레드가 읽을지 지정합니다. 덕분에 블록의 여러 스레드가 같은 입력을 반복 사용하도록 설계할 수 있지만, 쓰기가 끝나기 전에 다른 스레드가 읽지 않도록 동기화해야 합니다.

배열 덧셈은 각 입력을 한 번씩 읽으므로 공유 메모리로 복사해도 재사용 이득이 거의 없습니다. 오히려 저장·로드와 배리어를 추가할 수 있습니다. 공유 메모리는 빠르다는 이유로 모든 데이터를 거치는 장소가 아니라, 데이터 공유 패턴이 있을 때 사용하는 자원입니다.

## pinned memory와 Unified Memory

페이지 고정(pinned) 호스트 메모리는 운영체제가 일반 페이지처럼 자유롭게 이동시키지 않도록 등록·할당한 호스트 메모리입니다. CUDA의 호스트–장치 비동기 전송에서 중요한 역할을 합니다. 이 메모리를 사용해도 데이터가 GPU DRAM에 자동 복제되거나 PCIe 비용이 사라지지는 않습니다.

Unified Memory는 지원되는 환경에서 CPU와 GPU가 사용할 관리 메모리를 제공합니다. 페이지 이동이나 원격 접근 등의 구체적인 동작은 장치와 운영체제 기능에 따라 달라집니다. 포인터 사용을 단순하게 만들 수 있지만 페이지 폴트, 이동 비용과 동시 접근 조건을 없애는 기능은 아닙니다.

통합 GPU나 일관성 있는 CPU–GPU 연결을 가진 시스템에서는 명시적인 복사 모델이 달라질 수 있습니다. 그렇더라도 주소의 유효성, 접근 순서, 캐시와 메모리 대역폭은 남습니다. 물리적으로 메모리를 공유한다는 사실과 동기화가 필요 없다는 주장은 다릅니다.

NVIDIA의 [CUDA 메모리 모델](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-c-programming-guide/index.html#memory-hierarchy)과 [Unified Memory 설명](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-c-programming-guide/index.html#unified-memory-programming)은 각각 공간의 의미와 관리 메모리의 조건을 설명합니다. 이 시리즈는 실행 시점과 이동 비용을 드러내기 위해 명시적 장치 버퍼를 기본 경로로 유지합니다.

저장 위치를 알았다면 다음 질문은 시간입니다. CPU가 복사를 요청한 시점, GPU가 값을 읽는 시점, CPU가 버퍼를 재사용할 수 있는 시점을 구분해야 합니다.
