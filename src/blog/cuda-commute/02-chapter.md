GPU의 SM(Streaming Multiprocessor)은 여러 스레드의 실행 상태를 유지하며 명령어를 실행하는 처리 단위입니다. 하나의 SM에는 스케줄러, 레지스터 파일, 산술 유닛, 메모리 접근 유닛과 온칩 저장 공간이 있습니다. GPU에는 여러 SM이 있으며 이들은 장치의 메모리 시스템을 함께 사용합니다.

SM을 CPU 코어에 비유하면 구성 단위를 파악하는 데 도움이 됩니다. 그러나 CPU 코어와 동일한 기능·스케줄링·실행 폭을 가진다는 뜻은 아닙니다. 특히 제품 사양의 “CUDA 코어 수”를 CPU 코어 수처럼 해석해서는 안 됩니다.

## 명령어와 데이터를 공급하는 구조

CPU 코어에는 산술 유닛만 있는 것이 아닙니다. 명령어를 가져오고 해석하며, 피연산자가 준비되었는지 확인하고, 메모리 접근과 분기 이후의 실행을 관리하는 기능이 있습니다. GPU에도 명령어와 데이터를 실행 유닛에 공급하는 장치가 필요합니다. 차이는 이 제어 비용을 많은 데이터 병렬 실행에 걸쳐 분담하는 방식에 있습니다.

다음은 SM의 기능을 단순화한 그림입니다. 실제 파티션 수와 유닛 공유 방식은 GPU 세대에 따라 달라집니다.

```text
SM
 ├─ 명령어 공급·워프별 실행 상태
 ├─ 워프 스케줄러: 실행 가능한 워프의 명령 선택
 ├─ 레지스터 파일: 상주 스레드들의 피연산자·중간값
 ├─ 실행 유닛
 │   ├─ 부동소수점·정수 연산
 │   ├─ 로드/스토어
 │   └─ 세대별 특수 연산·행렬 연산
 └─ 공유 메모리·L1 계층
          ↕
     L2·장치 메모리
```

배열 덧셈을 수행하려면 먼저 두 입력을 읽어야 합니다. 필요한 값이 도착한 뒤에 덧셈 명령을 실행할 수 있고, 그 결과를 저장해야 합니다. 따라서 실행 유닛이 많아도 메모리 요청이 늦거나 의존성이 긴 경우에는 산술 유닛을 계속 채울 수 없습니다.

## 스레드 수, 상주 상태 수, 실행 폭

스레드는 프로그램의 실행 인스턴스입니다. 스레드마다 인덱스와 레지스터 값이 다를 수 있습니다. NVIDIA GPU는 한 블록의 스레드를 32개씩 워프(warp)로 묶어 명령 실행을 관리합니다. 워프 내부의 위치를 레인(lane)이라고 합니다. 레인은 논리적인 위치이지 영구 배정된 물리 ALU 번호가 아닙니다.

여기에는 세 가지 다른 수가 있습니다. 애플리케이션이 요청한 전체 스레드 수, SM에 실행 상태를 보관할 수 있는 스레드 수, 특정 종류의 명령을 한 사이클에 처리할 수 있는 수입니다. 수천 개 스레드가 상주한다고 수천 개 덧셈기가 한 사이클에 모두 동작하는 것은 아닙니다.

NVIDIA의 [Pascal 튜닝 가이드](https://docs.nvidia.com/cuda/pascal-tuning-guide/index.html)는 GP104의 SM당 FP32 유닛 128개와 워프 스케줄러 4개를 설명합니다. 같은 Pascal이라도 GP100은 구성이 다릅니다. 이 숫자는 GP104의 예이며, “모든 SM은 128코어”라는 CUDA 규칙이 아닙니다.

따라서 CUDA 코어는 독립적인 OS 스레드를 실행하는 CPU 코어보다 특정 산술 처리 자원에 가깝습니다. 워프 크기 32와 물리적 실행 폭을 무조건 동일시해서도 안 됩니다. 명령 종류와 세대에 따라 한 워프의 작업을 처리하는 방식과 처리량이 달라집니다.

## 메모리 대기를 숨기는 방법

워프 A가 입력 로드를 발행했지만 데이터가 아직 도착하지 않았다고 가정합니다. A의 다음 덧셈은 진행할 수 없습니다. SM은 피연산자와 실행 자원이 준비된 다른 워프 B의 명령을 발행할 수 있습니다. A의 메모리 요청이 끝나면 A가 다시 실행 가능한 후보가 됩니다.

```text
워프 A: 입력 로드 ────── 데이터 대기 ────── 덧셈 → 저장
워프 B:       입력 준비됨 → 덧셈 → 저장
워프 C:                         독립적인 연산
```

이는 대기 시간 자체를 제거한 것이 아닙니다. 다른 일을 수행해 전체 처리량에 미치는 영향을 줄인 것입니다. 이미 상주하는 워프의 상태는 레지스터 파일 등에 유지되므로, 매번 OS 스레드처럼 상태를 메모리에 저장하고 복구하는 과정이 필요하지 않습니다. 그렇다고 GPU의 모든 컨텍스트 전환이나 스케줄링 비용이 0이라는 뜻은 아닙니다.

CPU도 비순차 실행, SMT, 프리페치 등을 통해 대기와 다른 작업을 겹칩니다. GPU에도 캐시가 있습니다. 따라서 “CPU는 캐시, GPU는 스레드”라는 이분법보다 어느 구조에 더 많은 자원을 배분하고 어떤 병렬성을 활용하는지로 비교해야 합니다.

## 자원이 부족하면 상주할 수 없다

레지스터 파일과 공유 메모리는 유한합니다. 스레드 하나가 많은 레지스터를 사용하면 같은 SM에 상주시킬 수 있는 스레드 수가 줄어들 수 있습니다. 한 블록이 큰 공유 메모리를 요구해도 동시에 배치할 블록 수가 제한됩니다.

이 관계 때문에 블록 크기를 키우는 것만으로 성능이 좋아지지 않습니다. 실행 가능한 워프를 충분히 확보하는 것과 각 워프가 데이터를 효율적으로 처리하는 것은 별개의 문제입니다. 높은 점유율은 대기를 숨길 여지를 제공하지만, 연산이나 메모리의 병목을 자동으로 해결하지 않습니다.

이제 “SM은 실행 상태를 수용하고 명령을 발행하는 자원”이라는 기준이 생겼습니다. 다음 문서에서는 개발자가 요청하는 그리드와 블록이 이 자원에 어떻게 대응하는지 설명합니다.
