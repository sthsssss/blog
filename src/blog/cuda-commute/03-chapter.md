CUDA의 실행 구성은 물리적인 코어 배치를 지정하는 명령이 아닙니다. 개발자는 수행할 작업을 그리드·블록·스레드로 표현하고, 시스템은 사용 가능한 자원에 그 작업을 배치합니다. 이 분리가 있어야 같은 프로그램을 SM 수가 다른 장치에서 실행할 수 있습니다.

두 배열의 257개 원소를 더한다고 가정하겠습니다. 각 원소의 결과가 다른 원소에 의존하지 않으므로 출력 하나를 스레드 하나에 배정할 수 있습니다.

## 커널은 한 스레드가 수행할 일을 기술한다

```cpp
__global__ void Add(const float* a, const float* b,
                    float* c, unsigned int count)
{
    unsigned int i = blockIdx.x * blockDim.x + threadIdx.x;

    if (i < count)
    {
        c[i] = a[i] + b[i];
    }
}
```

`__global__`은 이 함수가 GPU 커널의 진입점임을 나타냅니다. 함수 본문은 전체 배열의 실행 순서를 기술하지 않습니다. 이 본문을 실행하는 각 스레드가 자신의 인덱스에 해당하는 원소를 처리합니다. `threadIdx.x`는 블록 안의 위치, `blockIdx.x`는 그리드 안의 블록 위치, `blockDim.x`는 블록의 스레드 수입니다.

호스트에서는 다음과 같이 작업을 구성합니다. `da`, `db`, `dc`는 준비된 장치 버퍼입니다.

```cpp
constexpr unsigned int count = 257;
constexpr unsigned int blockSize = 128;
unsigned int gridSize =
    count / blockSize + (count % blockSize != 0);

Add<<<gridSize, blockSize>>>(da, db, dc, count);
```

이 호출은 블록 3개와 블록당 스레드 128개, 총 384개의 논리적 실행 인스턴스를 요청합니다. 384개의 물리 코어를 예약하는 호출은 아닙니다.

| 블록 | 계산한 인덱스 | 실제로 기록하는 범위 |
| --- | --- | --- |
| 0 | 0–127 | 0–127 |
| 1 | 128–255 | 128–255 |
| 2 | 256–383 | 256만 기록 |

마지막 블록의 나머지 스레드는 조건을 통과하지 않습니다. 이 스레드들이 존재하지 않는 것은 아니며, 유효한 출력을 기록하지 않을 뿐입니다. 경계 검사는 `count`가 실제 할당 길이와 일치한다는 전제하에서만 안전합니다.

## 블록이 필요한 이유

스레드 블록은 단순히 인덱스 계산을 편하게 만드는 묶음이 아닙니다. 일반적인 CUDA 실행에서 한 블록은 한 SM에 배치되며, 블록의 스레드들은 공유 메모리와 블록 단위 배리어를 사용해 협력할 수 있습니다. 여러 블록이 한 SM에 함께 상주할 수 있지만 한 블록을 임의의 여러 SM으로 나누지는 않습니다.

이 규칙은 자원 요구량과 연결됩니다. SM이 블록의 레지스터·공유 메모리·스레드 자원을 수용할 수 있어야 블록을 실행 상태로 올릴 수 있습니다. 블록 크기가 허용 최대값 이내라도 자원 요구량에 따라 실행이 제한될 수 있습니다.

그리드의 블록들은 일반적으로 어느 순서로 실행될지 보장받지 않습니다. 블록 0이 끝난 뒤 블록 1이 시작한다고 가정하면 안 됩니다. 모든 블록이 동시에 상주할 수 있다는 전제도 사용할 수 없습니다. 다른 블록의 플래그를 무작정 기다리는 설계는 기다리는 블록들이 자원을 점유해 생산자 블록의 실행을 막을 수 있습니다.

이 제약 덕분에 런타임과 하드웨어는 GPU 크기에 맞춰 블록을 배치할 수 있습니다. NVIDIA의 [스레드 계층 설명](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-c-programming-guide/index.html#thread-hierarchy)은 이 독립성과 협력 범위를 프로그래밍 모델의 일부로 설명합니다. 협력적 실행과 이후 세대의 블록 클러스터는 별도 조건을 가진 확장입니다.

## 블록에서 워프로

128개 스레드의 블록은 4개의 워프로 구성됩니다. 블록은 배치와 협력의 단위이고, 워프는 SM에서 명령 실행을 관리하는 단위입니다. 둘은 역할이 다릅니다.

워프의 스레드들은 같은 커널에서 출발하지만 레지스터 값과 분기 결과는 다를 수 있습니다. 어떤 레인이 조건의 참 경로를, 다른 레인이 거짓 경로를 선택하면 활성 레인을 구분해 해당 경로의 명령을 처리해야 합니다. 이를 워프 분기 발산이라고 합니다.

예제의 마지막 워프에서는 일부 레인만 덧셈과 저장을 수행합니다. 이것은 정답을 유지하는 정상적인 경계 처리입니다. 분기가 존재한다는 이유만으로 잘못된 코드나 큰 성능 손실이라고 단정할 수 없습니다. 실제 비용은 활성 레인 수, 경로 길이, 컴파일러의 조건부 실행 변환 등에 따라 달라집니다.

Volta 이후에는 독립 스레드 스케줄링이 도입되어 스레드의 진행 상태를 더 세밀하게 관리합니다. 그렇다고 워프 단위 실행의 성격이 없어지거나 모든 레인이 독립 CPU 코어가 되는 것은 아닙니다. 특히 “같은 워프이므로 공유 메모리 교환은 자동으로 동기화된다”는 가정을 해서는 안 됩니다. [Volta 튜닝 가이드](https://docs.nvidia.com/cuda/volta-tuning-guide/index.html#independent-thread-scheduling)는 명시적인 워프 동기화가 필요한 경우를 설명합니다.

## OS 스레드와 구별하기

CPU의 호스트 스레드 하나가 이 커널을 제출해도 GPU에는 수백 또는 수백만 개의 논리적 스레드가 만들어질 수 있습니다. 이들은 OS가 각각 CPU 코어에 스케줄링하는 스레드가 아닙니다. GPU 작업을 제출하는 호스트 스레드, CUDA의 논리적 스레드, SM에 상주하는 워프를 별도로 그려야 합니다.

입력이 더 커지면 그리드의 블록 수를 늘릴 수 있습니다. 하지만 입력이 0이면 크기 0인 그리드를 제출하는 대신 호출을 생략합니다. 또한 예제의 32비트 인덱스 계산은 제한된 입력 크기를 전제로 합니다. 매우 큰 배열에서는 주소 계산의 정수 범위와 장치의 실행 크기 제한을 따로 확인해야 합니다.

이제 소스의 실행 인스턴스와 하드웨어 자원이 연결되었습니다. 다음 문서에서는 이 커널이 어떤 형태로 컴파일되어 장치에 전달되는지 살펴봅니다.
