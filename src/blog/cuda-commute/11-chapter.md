GPU가 신경망 계산에 널리 쓰이는 이유를 이해하려면 “많은 덧셈을 동시에 한다”에서 한 단계 더 나아가야 합니다. 행렬 연산은 입력을 여러 출력에서 재사용할 수 있고, 이를 타일 단위로 조직하면 데이터 이동에 비해 많은 산술 연산을 수행할 수 있습니다. Tensor Core는 이러한 행렬 연산의 일부를 처리하는 특수 실행 자원입니다.

먼저 일반적인 부동소수점 연산으로 구현할 수 있는 선형 계층부터 보겠습니다. 그러면 전용 행렬 유닛이 어느 위치에 추가되는지 구분할 수 있습니다.

## 벡터 하나를 변환하는 기준 구현

출력은 다음과 같습니다.

```text
y[o] = bias[o] + Σ weights[o * inputCount + i] * input[i]
```

가중치는 출력 행과 입력 열을 가진 row-major 배열입니다. 입력이 `[2, 3]`, 가중치 행이 각각 `[1, 2]`, `[-1, 1]`, bias가 `[0.5, -0.5]`이면 결과는 `[8.5, 0.5]`입니다. bias를 포함하므로 수학적으로는 affine 변환이며, 신경망에서는 흔히 linear layer라고 부릅니다.

출력 하나를 스레드 하나에 맡기면 다음 핵심 루프가 됩니다.

```cpp
float sum = bias[o];
for (unsigned int i = 0; i < inputCount; ++i)
{
    sum += weights[o * inputCount + i] * input[i];
}
output[o] = sum;
```

스레드의 `o`를 계산하고 출력 범위를 검사하는 부분은 전체 소스에 포함되어 있습니다. 이 구현은 동작을 확인하기 쉽지만 모든 shape에서 효율적인 구현은 아닙니다.

## 스레드 단위로 연속이어도 워프 단위로는 다를 수 있다

각 스레드는 자신의 가중치 행을 순서대로 읽습니다. 그러나 워프의 스레드들은 같은 반복 시점에 서로 다른 행의 같은 열을 읽습니다. 입력 크기가 784라면 이웃 스레드 사이의 가중치 주소 간격은 784 × 4 = 3136바이트입니다.

따라서 “스레드가 배열을 순회하므로 연속 접근”이라는 설명만으로는 충분하지 않습니다. 메모리 요청은 동시에 실행하는 레인들의 주소를 함께 보아야 합니다. 입력 벡터는 여러 스레드가 같은 원소를 읽는다는 점에서도 가중치와 접근 패턴이 다릅니다.

출력이 10개뿐이면 활성 스레드 수도 적습니다. 이 경우 GPU의 많은 SM을 충분히 사용하지 못할 수 있습니다. 모델의 연산이 행렬식으로 표현된다는 사실만으로 GPU가 효율적으로 실행한다고 결론 내릴 수 없습니다.

## 배치가 연산 구조를 바꾼다

여러 입력을 행으로 쌓으면 `Y = X Wᵀ + bias`라는 행렬 연산이 됩니다. 하나의 가중치가 여러 입력에 재사용되고, 입력의 타일도 여러 출력에 재사용됩니다. 이때 블록이 출력 타일을 맡고, 입력 타일을 공유 메모리나 레지스터에 준비하는 설계가 가능해집니다.

타일링의 목적은 계산식을 바꾸는 것이 아니라 데이터의 재사용 범위와 이동 횟수를 바꾸는 것입니다. 전역 메모리에서 읽은 데이터를 여러 곱셈·누적에 사용하면 연산 집약도가 높아질 수 있습니다. 타일 크기와 shape가 맞지 않는 경계에서는 남는 원소를 별도로 처리해야 합니다.

## Tensor Core는 CUDA를 대체하지 않는다

Tensor Core는 SM 안에서 특정 행렬 곱·누적 연산을 처리하는 실행 자원입니다. CPU에서 호출하는 별도의 GPU도 아니고 모든 스레드 명령을 처리하는 일반 코어도 아닙니다. 프로그램은 지원되는 명령이나 라이브러리를 통해 이 자원을 사용합니다.

일반 FP32 스칼라 루프를 작성했다고 모든 도구와 GPU에서 자동으로 Tensor Core 명령으로 바뀌는 것은 아닙니다. 입력 타입, 행렬 형태, 데이터 배치, 연산 인터페이스와 컴파일 경로가 맞아야 합니다. WMMA 같은 인터페이스는 여러 스레드의 협력으로 행렬 조각을 다루며, 지원되는 형태는 아키텍처에 따라 달라집니다.

Volta V100의 도입은 NVIDIA의 [Volta 아키텍처 백서](https://images.nvidia.com/content/volta-architecture/pdf/volta-architecture-whitepaper.pdf)에 설명되어 있습니다. 이후 세대에는 지원 정밀도와 행렬 명령이 확장됩니다. 이 시리즈의 GTX 1070에는 Tensor Core가 없으므로 해당 기능의 실행 검증을 했다고 주장하지 않습니다.

## 라이브러리가 맡는 책임

cuBLAS는 선형대수 연산을, cuDNN은 신경망 연산에 필요한 기능을 제공합니다. 이들은 CUDA 아래의 장치 드라이버가 아니라 CUDA를 이용하는 상위 라이브러리입니다. 호출자는 연산과 배열의 형태를 지정하고, 라이브러리는 지원되는 구현을 선택합니다.

라이브러리가 내부에서 전용 행렬 유닛을 사용하는지는 데이터 타입, 수학 모드, shape와 버전에 따라 달라집니다. 제품 사양에 Tensor Core 처리량이 높게 적혀 있어도 애플리케이션이 그 처리 경로를 이용하지 못하면 해당 성능이 나오지 않습니다. API의 조건은 [cuBLAS 문서](https://docs.nvidia.com/cuda/cublas/index.html)에서 확인해야 합니다.

직접 작성한 커널은 실행 구조를 이해하고 특수한 연산을 구현하는 데 유용합니다. 제품에서는 같은 수치 조건의 라이브러리를 비교 기준으로 삼아야 합니다. “직접 구현”과 “최적 성능”은 별개의 목표입니다.

## 정답과 수치적 동등성

병렬 합산은 연산 순서를 바꿀 수 있고, 곱셈과 덧셈을 FMA로 결합하면 반올림도 달라질 수 있습니다. 낮은 정밀도의 입력과 높은 정밀도의 누적을 사용하는 행렬 연산은 다시 다른 수치 조건을 가집니다.

따라서 출력 클래스 번호만 같다고 계산이 같다고 판단하지 않습니다. 유한 값 검사와 중간 텐서 비교, 절대·상대 오차를 함께 사용합니다. 허용 오차는 데이터 범위와 누적 길이에 맞춰 정해야 합니다. NVIDIA의 [부동소수점 설명](https://docs.nvidia.com/cuda/floating-point/index.html)은 이 차이를 분석하는 근거가 됩니다.

다음 문서에서는 단일 커널을 넘어 반복 요청, 여러 장치와 여러 사용자로 구조를 확장합니다. 여기에서도 핵심은 어떤 자원과 데이터를 누구와 공유하고, 어떤 경계를 넘어 이동시키는가입니다.
