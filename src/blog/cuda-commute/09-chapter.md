GPU의 성능은 실행 유닛의 수만으로 결정되지 않습니다. 각 명령에 필요한 데이터를 얼마나 효율적으로 공급하는지, 충분한 독립 작업이 있는지, 호스트가 작업을 얼마나 자주 제출하는지를 함께 봐야 합니다. 배열 덧셈은 계산량이 적어 이 관계를 확인하기 좋은 예입니다.

각 원소에서 FP32 입력 두 개를 읽고 결과 하나를 기록합니다. 논리적으로는 덧셈 한 번에 12바이트를 다룹니다. 이 계산만으로 실측 메모리 트래픽을 확정할 수는 없지만, 이 알고리즘이 많은 산술 연산을 수행하는 형태가 아니라는 점은 알 수 있습니다.

## 스레드 하나의 접근보다 워프의 주소를 본다

연속된 레인이 `a[i]`, `a[i + 1]`, `a[i + 2]`를 읽는다면 워프 전체의 요청 주소가 인접합니다. 메모리 시스템은 이러한 접근을 필요한 메모리 구간의 요청으로 병합할 수 있습니다. 이를 coalescing, 즉 메모리 접근 병합이라고 합니다.

Pascal을 포함한 compute capability 6.0 이상 장치의 기본 설명에서는 워프 접근을 처리하는 데 필요한 32바이트 구간 수를 생각할 수 있습니다. 모든 레인이 FP32 하나씩 읽고 첫 주소가 적절히 정렬되어 있으면 32개 값은 128바이트, 즉 4개 구간에 들어갑니다. 시작 주소가 어긋나면 추가 구간이 필요할 수 있습니다. 이는 NVIDIA의 [Best Practices Guide](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory)가 설명하는 모델입니다.

```text
연속 접근: lane 0 → a[0], lane 1 → a[1], lane 2 → a[2], ...
간격 접근: lane 0 → a[0], lane 1 → a[32], lane 2 → a[64], ...
```

두 경우 모두 스레드는 한 원소를 읽습니다. 하지만 워프가 요청하는 주소 구간 수는 다릅니다. “각 스레드가 한 번만 읽으니 효율적”이라는 판단으로는 이 차이를 볼 수 없습니다.

캐시 적중과 재사용도 있으므로 요청 구간 수를 그대로 DRAM 왕복 횟수라고 부르지는 않습니다. 요청의 병합, 캐시 계층에서의 처리, 최종 메모리 트래픽을 구분해야 합니다.

## 배열 덧셈은 왜 산술 유닛 수에 비례하지 않는가

연산 집약도는 전송한 데이터 양에 비해 수행한 연산량을 나타냅니다. 큰 배열을 한 번씩 읽고 쓰는 단순 모델에서는 배열 덧셈이 약 1/12 FLOP/byte입니다. 장치 메모리에서 데이터를 공급하는 속도가 제한되면 산술 유닛을 늘려도 데이터를 더 빨리 받을 수 없습니다.

Roofline 모델은 가능한 성능을 연산 처리량의 상한과 메모리 대역폭으로부터 생각하게 합니다.

```text
가능한 연산 처리량 ≤ min(연산 성능 상한, 메모리 대역폭 × 연산 집약도)
```

이것은 달성 성능을 보장하는 공식이 아닙니다. 의존성, 명령 발행, 캐시, 점유율과 제출 비용 때문에 더 낮을 수 있습니다. 특히 257개처럼 작은 입력은 장치 전체를 활용하기에도 부족하므로 큰 배열의 대역폭 모델만으로 설명하면 안 됩니다. Roofline의 원래 목적은 병목의 상한을 구분하는 것이며, Williams·Waterman·Patterson의 [Berkeley 기술 보고서](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/EECS-2008-134.html)에서 배경을 확인할 수 있습니다.

## 전체 지연과 커널 시간을 분리하기

```text
전체 요청: 입력 준비 + 호스트→장치 전송 + 커널 + 장치→호스트 전송 + 결과 사용
커널 구간:                         GPU 계산
```

CPU 시계로 커널 제출 호출만 재면 대체로 작업을 제출하는 비용에 가까운 값을 얻습니다. 결과가 실제로 준비되는 시간을 재려면 필요한 복사와 완료 대기를 측정 구간에 포함해야 합니다.

CUDA 이벤트를 같은 스트림의 앞뒤에 기록하면 장치의 시간 구간을 측정할 수 있습니다. 종료 이벤트 완료 뒤 경과 시간을 읽습니다. 다만 그 사이에 장치 대기나 호스트 제출의 빈 구간이 들어갈 수 있으므로 “산술 유닛이 바쁘게 일한 시간”과 항상 같지는 않습니다.

예제는 이벤트 기록·대기·시간 조회를 실행하지만 성능 벤치마크로 사용하지 않습니다. 정확성 확인용 작은 입력과 자주 동기화하는 구조에서 얻은 시간을 일반적인 처리량으로 발표해서는 안 됩니다.

## 관측에서 설계 변경으로

먼저 초기화와 첫 코드 적재 비용을 구별합니다. 그다음 요청의 대부분이 전송인지, 커널인지, CPU의 제출과 대기인지 확인합니다. 타임라인 도구는 작업 사이의 공백과 중첩을 확인하는 데, 커널 프로파일러는 메모리 처리와 실행 자원 사용을 분석하는 데 유용합니다. 장치 세대에 따라 도구 지원 범위가 다르므로 사용 가능성을 먼저 확인합니다.

전송이 대부분이라면 가중치나 중간 결과를 장치에 유지하는 설계가 우선일 수 있습니다. 작은 커널 제출이 반복되면 작업 결합이나 CUDA Graph가 후보가 될 수 있습니다. 커널이 메모리 병목이면 주소 배치와 데이터 재사용을 검토합니다. 점유율 수치만 올리는 변경은 이 판단을 대신하지 못합니다.

공유 메모리는 다음 문서에서 다룹니다. 배열 덧셈에는 재사용이 거의 없지만, 여러 스레드가 같은 입력을 사용하는 계산에서는 메모리 이동량 자체를 줄일 수 있습니다. 이 차이가 새로운 자원을 도입할 이유입니다.
