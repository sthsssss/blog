GPU를 이해하려면 명령어가 실행되는 장치와 프로그램이 그 장치를 사용하는 방법을 함께 살펴봐야 합니다. CUDA 함수의 호출 방법만 알아서는 스레드 수를 늘렸는데 성능이 낮아지는 이유를 설명하기 어렵습니다. 반대로 GPU의 블록 다이어그램만 알아서는 실행 파일에 들어 있는 코드가 장치에 적재되는 경로를 설명할 수 없습니다.

이 시리즈는 CPU의 명령어 실행, 가상 메모리, 컴파일과 링크를 알고 있는 개발자를 대상으로 합니다. 이 지식을 GPU에 그대로 적용하는 대신, 어떤 관계가 유지되고 어느 지점에서 다른 모델이 필요한지 설명합니다. 목표는 API 목록을 외우는 것이 아니라 시스템의 구조를 그려 보고 실행 결과와 성능을 추론할 수 있게 하는 것입니다.

## 세 가지 지도를 겹쳐서 읽기

먼저 물리적인 자원을 구분합니다. 독립형 GPU를 장착한 시스템에는 CPU와 시스템 메모리 외에 GPU와 장치 메모리가 있습니다. GPU 내부에는 여러 SM이 있고, 각 SM에는 명령 발행을 담당하는 스케줄러와 계산·메모리 접근을 수행하는 실행 유닛이 있습니다. 이 구조는 “데이터와 실행 상태가 어디에 있는가”에 답합니다.

두 번째 지도는 프로그래밍 모델입니다. CUDA의 그리드·블록·스레드는 개발자가 작업을 표현하는 단위입니다. 물리적인 SM·실행 유닛과 같은 대상이 아닙니다. 블록이 SM에 배치되고 스레드들이 워프로 묶여 실행되는 관계를 연결해야 합니다.

세 번째 지도는 소프트웨어입니다. 컴파일러는 장치용 코드를 만들고, 런타임과 드라이버는 코드·메모리·작업을 관리합니다. 운영체제는 장치 접근과 자원 관리에 참여합니다. 이 지도는 “누가 무엇을 변환하고 제출하는가”에 답합니다.

```text
프로그램의 표현       실행을 연결하는 소프트웨어       물리적인 실행 자원
커널·그리드·블록  →   컴파일러·런타임·드라이버    →    GPU의 SM·실행 유닛
포인터·배열       →   주소 매핑·할당·전송         →    캐시·장치 메모리
스트림·이벤트     →   작업 순서·완료 관리         →    실행·복사 엔진
```

화살표는 일대일 대응이 아닙니다. 한 스트림이 SM 하나를 소유하지 않으며, CUDA 스레드 하나가 CUDA 코어 하나를 전용으로 사용하지도 않습니다. 이 대응의 조건과 한계를 본문에서 구체적으로 다룹니다.

## 전체를 관통하는 예제

두 배열의 같은 위치를 더하는 `c[i] = a[i] + b[i]`를 사용합니다. 계산이 단순하므로 어떤 코드가 실행되고, 어느 주소에서 값을 읽고, 결과가 언제 CPU에서 보이는지에 집중할 수 있습니다. 257개 원소에서 시작하고, 성능을 논의할 때에는 더 큰 배열과 반복 요청으로 확장합니다. 공유와 재사용이 필요한 시점에 합산과 행렬 연산을 도입합니다.

[전체 예제 소스](/downloads/cuda-commute/examples.cu)는 별도로 내려받을 수 있습니다. 문서의 C++ 예제는 설명을 위한 독립 프로그램이며, 다른 언어로 진행하는 학습 프로젝트의 구현을 대체하지 않습니다.

## 적용 범위

기준 장치는 독립형 NVIDIA GPU입니다. 실제 실행은 Pascal 계열 GTX 1070과 CUDA Toolkit 12.6에서 확인합니다. 이 장치에는 Tensor Core가 없으므로 이후 세대의 기능은 실행 결과가 아니라 문헌에 근거한 확장으로 구분합니다. 통합 GPU, CPU–GPU 일관성 연결, 다중 GPU 역시 기본 모델과 무엇이 달라지는지를 설명합니다.

GPU 전체에는 그래픽스, 디스플레이, 영상 코덱 등의 기능도 있습니다. 이 시리즈는 이들의 위치를 설명하되 세부 렌더링 알고리즘보다 범용 계산의 실행 경로에 집중합니다. 한 제품의 레지스터 수나 캐시 구성을 모든 세대의 규칙으로 일반화하지 않습니다.

한국어 개인 블로그에서 참고한 설명 방식과 NVIDIA·Microsoft의 기술 근거는 부록에서 구분하여 소개합니다. 본문은 해당 글을 읽지 않아도 따라갈 수 있도록 구성했습니다.
