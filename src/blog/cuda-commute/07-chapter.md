GPU 작업을 요청하는 API의 반환과 GPU 작업의 완료는 같은 사건이 아닙니다. CPU는 요청을 제출한 뒤 다른 일을 할 수 있고, GPU는 나중에 그 요청을 수행할 수 있습니다. 따라서 비동기 프로그램에서는 어느 작업이 먼저 끝나야 하는지를 표현하고, 메모리가 마지막으로 사용되는 시점까지 유지해야 합니다.

이 문제는 CPU의 비동기 I/O와 유사하지만 실행 주체가 GPU와 복사 엔진으로 확장됩니다. CUDA 스트림과 이벤트는 이 실행 순서를 다루는 수단입니다.

## 스트림은 순서를 나타낸다

스트림은 작업을 순서 있게 제출하는 논리적인 단위입니다. 동일 스트림의 작업은 순서에 따른 의존성을 가집니다. 배열 덧셈의 두 입력 복사, 커널, 결과 복사를 같은 스트림에 넣으면 뒤 작업은 필요한 앞 작업의 결과를 사용할 수 있습니다.

```text
CPU:  입력 복사 제출 → 커널 제출 → 결과 복사 제출 → 완료 대기 → 결과 읽기
GPU:       입력 복사 완료 → Add 실행 완료 → 결과 복사 완료
```

스트림 하나가 OS 스레드 하나나 SM 하나에 대응하지는 않습니다. 스트림을 두 개 만들었다고 GPU가 절반씩 나뉘지도 않습니다. 여러 스트림의 작업을 동시에 실행할 수 있는지는 하드웨어 기능, 자원 요구량과 작업 사이의 의존성에 달려 있습니다.

예제는 `cudaStreamCreateWithFlags(..., cudaStreamNonBlocking)`으로 명시적인 스트림을 만듭니다. 여기서 NonBlocking은 주로 legacy default stream과의 암묵적 동기화 관계를 바꾸는 플래그입니다. 모든 API가 CPU를 절대 대기시키지 않는다는 뜻이 아닙니다.

## Async라는 이름만으로 중첩을 판단하지 않는다

`cudaMemcpyAsync`는 스트림에 복사를 요청하는 API입니다. 호스트 메모리의 종류와 전송 방향 등에 따라 호출의 실제 호스트 동기화 동작이 달라질 수 있습니다. NVIDIA의 [API 동기화 동작 설명](https://docs.nvidia.com/cuda/cuda-runtime-api/api-sync-behavior.html)은 함수 이름만으로 모든 경우를 판단하지 않도록 조건을 구분합니다.

복사와 계산이 겹치려면 서로 독립적인 작업이어야 하고 장치가 해당 동시 실행을 지원해야 합니다. 호스트–장치 전송에서는 pinned memory 등의 조건도 중요합니다. 같은 배열을 GPU가 읽는 동안 CPU가 덮어쓰는 것은 유용한 중첩이 아니라 데이터 경합입니다.

배열 덧셈 한 번은 입력이 도착해야 계산할 수 있습니다. 이 요청 내부의 의존성은 스트림을 늘려도 사라지지 않습니다. 중첩을 만들려면 입력을 여러 청크로 나누거나, 이전 요청을 계산하는 동안 다음 요청의 독립된 버퍼를 전송하는 식으로 구조를 바꿔야 합니다.

## 이벤트는 진행 지점을 연결한다

스트림 A에서 결과를 만들고 스트림 B에서 그 결과를 사용한다면 명시적인 연결이 필요합니다.

```cpp
Check(cudaEventRecord(ready, streamA));
Check(cudaStreamWaitEvent(streamB, ready, 0));
```

이벤트는 A에서 앞서 제출된 작업 이후의 진행 지점을 기록합니다. B는 그 이벤트가 완료된 뒤 후속 작업을 수행하도록 합니다. CPU가 그 자리에서 A 전체의 완료를 기다려야 하는 구조와 다릅니다.

이벤트 대기는 데이터를 복사하지 않습니다. 이미 같은 장치에서 접근 가능한 버퍼에 대해 생산자와 소비자의 순서를 정하는 것입니다. 별도 장치나 호스트로 데이터가 필요하다면 해당 데이터 이동도 설계해야 합니다.

## 완료와 메모리 수명

예제는 입력·출력 버퍼를 할당한 뒤 스트림을 만듭니다. C++의 역순 소멸을 이용해 스트림 객체가 버퍼보다 먼저 정리되도록 했습니다. 정상 경로에서는 `cudaStreamSynchronize`의 성공을 확인하고 결과를 비교합니다. 예외 경로에서는 스트림 래퍼가 완료를 가능한 범위에서 기다린 뒤 버퍼 정리가 진행되도록 합니다.

소유권을 가진 객체가 존재한다는 사실만으로 비동기 접근이 안전해지는 것은 아닙니다. 객체를 너무 일찍 소멸시키거나 메모리 내용을 재사용하면 GPU가 아직 그 주소를 사용할 수 있습니다. 자원 수명은 CPU 함수의 범위뿐 아니라 장치 작업의 완료와 연결되어야 합니다.

```text
할당 ── CPU 입력 작성 ── GPU 전송·계산·복사 ── 완료 확인 ── 재사용/해제
                          이 구간에는 충돌하는 접근 금지
```

## 동시 실행을 설계하는 단위

반복 요청을 처리하는 서버에서는 “스트림 몇 개”보다 “동시에 진행할 요청이 어떤 버퍼를 사용하는가”가 먼저입니다. 요청마다 작업 버퍼를 분리하거나, 완료 이벤트가 확인된 버퍼만 풀로 돌려주는 방식이 필요합니다.

여러 호스트 스레드가 같은 스트림에 작업을 제출하는 경우에도 애플리케이션이 기대한 제출 순서를 별도로 보장해야 합니다. GPU의 순서 보장이 호스트 코드의 경쟁 조건을 해결하지는 않습니다.

스트림과 이벤트의 역할을 이해하면 다음 층의 문제도 구분할 수 있습니다. 커널 제출이 실패한 경우와, 제출은 되었으나 나중에 GPU에서 잘못된 주소에 접근한 경우는 오류를 관찰하는 시점이 다릅니다. 다음 문서는 이 오류와 운영체제의 장치 관리 경계를 연결합니다.
