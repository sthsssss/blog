CUDA는 작업을 그리드, 블록 및 스레드로 표현합니다. 이 계층은 애플리케이션이 지정하는 작업의 구조입니다. GPU는 이 구조를 실제 실행 자원에 배치하고, 블록의 스레드를 워프 단위로 처리합니다.

이 문서에서는 논리적인 작업 배치와 물리적인 실행을 구분합니다. 두 관점을 구분하면 블록 수가 GPU의 연산 장치 수보다 많아도 실행할 수 있는 이유와, 같은 블록의 스레드만 협력할 수 있는 기본 범위를 이해할 수 있습니다.

## 그리드에서 블록으로

커널 호출 한 번으로 실행하는 블록 집합을 그리드라고 합니다. 각 블록에는 정해진 수의 스레드가 있습니다. 다음 호출은 블록 세 개를 만들고 각 블록에 스레드 128개를 배치합니다.

```cpp
FillPattern<<<3, 128>>>(deviceOutput, 257);
```

블록마다 `threadIdx.x`는 0부터 다시 시작합니다. 블록 번호는 `blockIdx.x`로 구분합니다. 따라서 블록과 스레드의 번호를 함께 사용해야 전체 배열의 위치를 선택할 수 있습니다.

```text
그리드
 ├─ 블록 0: 스레드 0 ~ 127
 ├─ 블록 1: 스레드 0 ~ 127
 └─ 블록 2: 스레드 0 ~ 127
```

여기서 블록은 단순히 번호를 묶는 단위가 아닙니다. 같은 블록의 스레드는 블록 전용 공유 메모리에 접근하고 블록 범위의 배리어를 사용할 수 있습니다. 데이터 교환과 동기화의 범위가 작업 배치에 포함되는 것입니다.

## 스트리밍 멀티프로세서에 배치

GPU에는 스트리밍 멀티프로세서(SM)라는 실행 단위가 여러 개 있습니다. SM에는 산술 연산 장치뿐 아니라 스레드 상태를 저장할 레지스터와 명령을 선택하는 스케줄러 등의 자원이 포함됩니다.

블록이 실행되려면 해당 블록에 필요한 자원을 확보해야 합니다. 일반적인 CUDA 실행에서 블록의 스레드는 한 SM에 배치됩니다. 한 SM이 블록 하나만 처리하는 것은 아닙니다. 자원이 허용하면 여러 블록이 함께 상주할 수 있습니다.

예를 들어 블록 하나가 많은 레지스터를 사용하면 같은 SM에 함께 배치할 수 있는 블록 수가 줄 수 있습니다. 블록 수를 늘렸다는 사실만으로 동시에 실행 중인 블록 수가 같은 비율로 늘지는 않습니다.

일반 커널에서는 블록 사이의 실행 순서를 가정하지 않습니다. 블록 0이 먼저 끝나야 블록 1을 실행한다는 계약도 없습니다. 앞의 패턴 예제는 블록이 서로 다른 출력 위치에 기록하므로 순서에 의존하지 않습니다. 반면 블록 간 통신이 필요하면 그 의존성을 별도의 실행 단계나 지원되는 동기화 방식으로 표현해야 합니다.

## 블록에서 워프로

NVIDIA GPU는 블록의 스레드를 32개씩 묶은 워프로 구성합니다. 워프는 명령 실행을 이해하는 기본 단위입니다. 이 문서의 1차원 블록에서는 연속된 스레드 번호가 같은 워프에 속합니다.

| 블록 안의 스레드 번호 | 워프 |
| --- | --- |
| 0–31 | 첫 번째 워프 |
| 32–63 | 두 번째 워프 |
| 64–95 | 세 번째 워프 |
| 96–127 | 네 번째 워프 |

블록당 스레드가 128개이면 워프 네 개가 있습니다. 블록 크기를 130으로 변경하면 다섯 번째 워프가 필요하며 그 워프에는 유효한 스레드가 두 개만 있습니다.

워프의 각 위치를 레인이라고 합니다. 레인은 스레드의 실행 상태를 설명하는 위치이지, 프로그램 전체에 걸쳐 고정된 물리적 코어 번호가 아닙니다. 스레드 하나와 CUDA 코어 하나를 영구적으로 짝짓는 방식으로 실행을 이해하면 안 됩니다.

워프에 스레드 32개가 있다는 사실도 모든 명령이 한 클록에 32개 연산 장치에서 끝난다는 뜻은 아닙니다. 명령의 종류와 GPU 세대에 따라 필요한 실행 자원과 처리 주기가 달라집니다.

NVIDIA의 [워프와 SIMT 설명](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html#warps-and-simt)은 이러한 논리적 스레드와 하드웨어 실행 묶음의 관계를 설명합니다.

## 이 구조가 유지되는 이유

G80 이후 SM의 내부 구조와 GPU 전체의 SM 수는 달라졌습니다. 하지만 애플리케이션이 블록과 스레드로 작업을 표현하는 방식은 유지되었습니다. 하드웨어가 실행 자원을 늘리더라도 프로그램이 물리적 배치를 직접 지정하지 않으므로 같은 작업 구조를 사용할 수 있습니다.

이것이 같은 소스의 실행 가능성과 같은 성능이 서로 다른 문제인 이유이기도 합니다. 커널이 정상 동작하더라도 블록 크기, 레지스터 사용량 및 메모리 접근이 새 장치에서 최적이라는 보장은 없습니다.

다음 문서에서는 같은 워프의 스레드가 서로 다른 조건을 만족할 때 실행이 어떻게 달라지는지 살펴봅니다.
