GPU는 CPU의 명령어 일부를 대신 실행하는 단순한 ALU가 아닙니다. 독립형 GPU는 자체 명령어 실행 장치와 메모리 계층을 가진 프로세서입니다. CPU에서 실행되는 애플리케이션이 GPU를 사용하려면 작업에 필요한 코드와 데이터를 준비하고, 장치에 실행을 요청한 뒤 결과를 받아야 합니다.

따라서 첫 번째로 구분할 것은 “CPU에서 어떤 함수를 호출했는가”와 “어느 프로세서가 그 함수의 계산을 수행하는가”입니다. 두 배열을 더하는 계산으로 이 경계를 살펴보겠습니다.

## CPU의 배열과 GPU의 배열

CPU만 사용하는 프로그램에서는 프로세스의 가상 주소로 배열을 읽고 결과를 기록합니다. 주소는 MMU와 페이지 테이블을 통해 물리 메모리에 연결되며, 실제 접근은 캐시 계층을 거칠 수 있습니다. 같은 프로세스 안에서 함수를 호출한다고 데이터를 다른 프로세서의 메모리로 보내지는 않습니다.

독립형 GPU를 사용하는 가장 단순한 경로는 다릅니다. 호스트 배열을 준비하고, GPU가 접근할 장치 버퍼를 할당하고, 입력을 복사한 뒤 장치 코드를 실행합니다. 계산이 끝나면 결과를 호스트로 복사합니다. 여기서 호스트는 애플리케이션을 제어하는 CPU 측을, 장치는 계산을 맡는 GPU 측을 뜻합니다.

```text
CPU ── 캐시 ── 시스템 DRAM
 │
 │ 호스트 연결 경로(일반적인 독립형 GPU에서는 PCIe)
 │
GPU의 작업 수신·복사 기능
 ├─ SM들: 계산 명령어 실행
 └─ L2·메모리 컨트롤러 ── 장치 DRAM(GDDR 또는 HBM)
```

이 그림은 책임을 나타낸 개념도입니다. 모든 데이터가 하나의 직렬 경로를 따른다는 배선도가 아닙니다. 실제 칩에는 내부 연결망, 여러 메모리 파티션, 캐시와 실행 엔진이 있습니다.

GPU 메모리에 배열을 할당했다고 CPU가 그 주소를 일반 포인터처럼 역참조할 수 있는 것은 아닙니다. 반대로 CPU의 일반 배열 주소를 GPU가 항상 읽을 수 있는 것도 아닙니다. 공유·매핑·통합 메모리는 뒤에서 설명할 별도 조건입니다. 우선 분리된 저장 공간과 명시적인 복사를 기준으로 삼으면 데이터 이동의 비용이 드러납니다.

## 그래픽 장치가 계산 장치가 된 이유

3차원 화면을 만들 때에는 많은 정점을 변환하고 많은 화면 위치의 색을 계산합니다. 작업 하나의 결과를 즉시 얻는 것보다 수많은 작업을 정해진 시간 안에 처리하는 것이 중요합니다. 이러한 요구는 많은 데이터에 유사한 연산을 적용하는 하드웨어와 높은 메모리 대역폭의 발전을 이끌었습니다.

그래픽 파이프라인은 모두 같은 종류의 프로그램으로 구성되지 않습니다. 정점·픽셀 셰이더처럼 개발자가 프로그램을 제공하는 단계와, 래스터화처럼 특정 작업을 수행하는 기능이 함께 있습니다. CUDA는 이 전체 파이프라인을 실행하는 API가 아닙니다. GPU의 프로그래밍 가능한 계산 자원을 범용 작업에 사용하는 경로입니다.

프로그래밍 가능한 셰이더가 등장한 뒤 연구자들은 배열 계산을 텍스처 입력과 렌더링 출력으로 표현했습니다. GPU의 산술 처리량은 활용할 수 있었지만, 계산을 그래픽스 API의 형태에 맞춰야 했습니다. “배열을 더한다”는 문제를 해결하기 위해 그래픽 처리의 데이터 표현과 실행 절차를 알아야 했던 것입니다.

Stanford의 Ian Buck과 공동 연구진이 발표한 [Brook for GPUs](https://graphics.stanford.edu/papers/brookgpu/)는 SIGGRAPH 2004 연구입니다. C 기반 스트림 언어와 컴파일러·런타임으로 이러한 변환의 일부를 감쌌습니다. 이 연구의 의의는 GPU가 계산을 할 수 있다는 사실을 넘어, 계산에 맞는 개발 인터페이스가 필요하다는 문제를 구체화한 데 있습니다.

## NVIDIA가 제공해야 했던 것은 언어만이 아니었다

CUDA는 개발자가 커널이라는 계산 함수를 작성하고 많은 실행 인스턴스를 요청하도록 합니다. 이를 실현하려면 언어 확장, 컴파일러, 실행 API, 드라이버와 하드웨어가 맞물려야 합니다. C 문법 몇 개를 추가하는 것만으로는 장치 메모리 접근이나 실행 스케줄링을 제공할 수 없습니다.

NVIDIA의 [2007 회계연도 연차보고서](https://www.sec.gov/Archives/edgar/data/1045810/000104581007000008/fy2007annualreportonform10-k.htm)는 CUDA 지원 GeForce 8의 공급과 과학·공학 분야의 GPU Computing을 사업 방향으로 설명합니다. [SIGGRAPH 2007 자료](https://www.nvidia.com/content/events/siggraph_2007/supercomputing.html)는 GeForce·Quadro와 함께 계산용 Tesla 제품군을 소개합니다. 기존 그래픽 시장에서 공급하던 GPU를 더 넓은 계산 시장에 제공하려면 개발 도구와 소프트웨어 생태계가 필요했다는 관계를 이 자료에서 읽을 수 있습니다. 이것은 플랫폼 전략에 대한 해석이며 당시 성공이 보장되어 있었다는 뜻은 아닙니다.

G80 세대에서는 정점·픽셀 등의 프로그래밍 가능한 작업에 통합 실행 자원을 배정하는 구조가 중요한 기반이 되었습니다. 다만 통합 셰이더가 래스터화나 디스플레이 같은 모든 전용 기능을 없앴다는 의미는 아닙니다. NVIDIA의 [GTX 200 기술 문서](https://www.nvidia.com/docs/io/55506/geforce_gtx_200_gpu_technical_brief.pdf)는 이전 GeForce 8800에서 이어지는 이 구조를 설명합니다.

## 초기 사용자는 무엇을 평가했는가

CUDA Toolkit 1.0은 [NVIDIA 도구 보관소](https://developer.nvidia.com/cuda-toolkit-archive/)에 2007년 6월 릴리스로 기록되어 있습니다. 초기의 C 기반 환경과 현재의 CUDA C++ 기능 전체는 구별해야 합니다.

2007년 Belleman 등의 [중력 N체 시뮬레이션 연구](https://arxiv.org/abs/0707.0438)는 힘 계산을 GPU에 맡기고 적분을 CPU에 남겨 두었습니다. 초기 사용 사례부터 이미 “프로그램 전체의 GPU 이전”보다 “계산량이 큰 부분의 분리”가 중요했습니다. 2008년 Che 등의 [애플리케이션 성능 연구](https://www.cs.virginia.edu/~skadron/Papers/cuda_jpdc08.pdf)에서는 메모리 접근과 동기화 제약에 맞춘 설계가 필요했음을 확인할 수 있습니다.

이 사례를 개발자 전체의 여론으로 확대할 수는 없습니다. 다만 도입한 개발자들이 처리 속도뿐 아니라 수치 정확성, 데이터 배치와 구현 비용을 평가했다는 점은 분명합니다. 접근하기 쉬운 언어가 제공되어도 CPU용 알고리즘이 그대로 좋은 GPU 프로그램이 되는 것은 아니었습니다.

## 배열 덧셈으로 되돌아가기

`c[i] = a[i] + b[i]`는 원소 사이의 의존성이 없어 여러 위치를 동시에 계산하기 좋습니다. 하지만 호스트에서 입력을 복사하고 결과를 회수하는 비용까지 고려하면 작은 배열에서는 CPU보다 늦을 수 있습니다. GPU를 사용하는 판단은 계산 명령어의 개수와 데이터 이동을 함께 고려해야 합니다.

이제 장치의 경계가 정해졌습니다. 다음 문서에서는 그 안으로 들어가 SM이 어떤 상태를 저장하고 어떤 방식으로 명령어를 실행하는지 살펴봅니다. 이 구조를 알아야 CUDA의 “수천 개 스레드”가 물리적으로 무엇을 의미하는지 설명할 수 있습니다.
