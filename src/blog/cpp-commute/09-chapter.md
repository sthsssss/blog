앞 편에서는 참조를 어떤 표현식에 연결할 수 있는지 확인했습니다. 컴파일이 가능한 연결이라고 해서 대상이 계속 남아 있는 것은 아닙니다. 이번에는 원본이 만들어지고 사라지는 순서를 따라가겠습니다. 객체가 유효하게 존재하는 기간을 수명(lifetime)이라고 합니다.

지역 객체는 보통 선언에서 초기화되고 해당 블록을 떠날 때 수명이 끝납니다. 클래스 객체는 이때 소멸자(destructor)라는 정리 함수를 호출할 수 있습니다. 현재의 단순한 `Gradient`는 별도 정리 코드가 없어도 수명은 끝납니다. 메모리에 예전 비트가 남아 있는지와 유효한 객체가 존재하는지는 다른 문제입니다. [표준 초안: 객체 수명](https://eel.is/c++draft/basic.life)

**참조를 담은 객체가 사라져도 바깥의 원본은 남을 수 있습니다.**

```cpp
struct View { const Gradient& data; };
Gradient original{0, 255};
const Gradient* saved = nullptr;
{
    View view{original};
    saved = &view.data;
}
```

`view.data`는 외부의 `original`에 연결되어 있습니다. `&view.data`는 그 원본의 주소를 구하므로 `saved`도 `original`을 직접 가리킵니다. 블록이 끝나면 `view`는 사라지지만 원본과 `saved`는 바깥에 남습니다. 다음 문장에서 `saved->start`를 읽으면 0입니다. 사라진 `view`를 거쳐 원본을 찾는 구조가 아닙니다.

원본까지 안쪽 블록에 선언하면 조건이 달라집니다. 그 경우 블록이 끝난 뒤 `saved`에 주소 값이 남더라도 원본의 수명은 끝났습니다. 이런 포인터나 참조를 댕글링(dangling)이라고 합니다. 주소 값의 존재만으로 대상의 존재를 판단할 수 없습니다.

**지역 객체의 참조를 반환하면 원본이 먼저 사라집니다.**

```cpp
Gradient& bad() {
    Gradient local{0, 255};
    return local;
}
```

반환문은 새 결과 객체를 만들지 않고 `local`에 연결된 참조를 제공합니다. 그러나 함수가 끝나면 `local`의 수명이 끝납니다. 호출자가 반환된 참조로 필드를 읽거나 쓰는 것은 유효하지 않습니다. 이번 Clang과 GCC는 이 함수에 경고를 냈지만, 모든 잘못된 수명을 언어가 컴파일 오류로 차단하는 것은 아닙니다.

`const Gradient&`로 반환하거나 호출자가 const 참조로 받는다고 지역 객체의 수명이 늘어나지는 않습니다. 수정 권한을 제한하는 const와 수명을 연장하는 특정 언어 규칙을 분리해서 봐야 합니다.

**새 값의 임시 객체에 직접 연결하면 수명이 연장될 수 있습니다.**

6편의 `Gradient make_gradient() { return Gradient{0, 255}; }`를 사용합니다.

```cpp
{
    const Gradient& read = make_gradient();
    Gradient&& edit = make_gradient();
    edit.start = 100;
}
```

두 호출은 각각 새 결과 객체를 만듭니다. 지역 참조를 값 반환 결과에 직접 연결하므로 임시 객체의 수명이 각 참조의 수명까지 연장됩니다. 블록 안에서 `read`와 `edit`를 사용할 수 있고 블록을 떠나면 해당 임시 객체도 소멸합니다. 우측값 참조를 사용한 둘째 줄도 같은 수명 연장 사례입니다. [표준 초안: 임시 객체의 수명](https://eel.is/c++draft/class.temporary)

반면 이미 이름이 있는 `data`에 참조를 하나 더 만든다고 그 원본의 일반적인 수명이 늘어나지는 않습니다. 직접 임시 결과에 연결한 경우에 적용된 규칙입니다.

**참조를 반환하는 함수를 거치면 임시 객체의 수명은 다르게 끝납니다.**

```cpp
const Gradient& identity(const Gradient& g) {
    return g;
}

const Gradient& read = identity(make_gradient());
```

임시 객체는 `identity`의 인수로 만들어지고 함수가 실행되는 동안 살아 있습니다. 함수는 그 객체에 대한 참조를 반환합니다. 호출자의 선언문이 끝나는 세미콜론에서 이 임시 객체가 소멸하므로 다음 문장에서 `read.start`를 읽으면 안 됩니다.

반환받은 참조에 다시 연결하는 것은 이미 정해진 대상의 수명을 추가로 늘리는 연산이 아닙니다. `const Gradient& direct = make_gradient();`와 마지막 코드는 겉모양이 비슷해도 임시 객체가 참조에 연결되는 과정이 다릅니다.

첨부 예제에서는 객체가 생성될 때 생존 개수를 늘리고 소멸할 때 줄이는 `Watched` 타입으로 이 순서를 관찰했습니다. 직접 받은 임시 객체는 블록 안에서 1개가 살아 있었고, 블록 뒤에는 0개였습니다. `identity`를 거친 선언은 세미콜론 뒤에 이미 0개였습니다. 무효가 된 참조를 역참조해서 출력값을 추측하지는 않았습니다. GCC는 이 마지막 결합에도 댕글링 가능성 경고를 냈습니다.

**멤버 참조의 유효성은 그 멤버가 속한 원본을 따라갑니다.**

6편의 `owner.get_ref()`가 직접 가진 `owner.data`를 반환했다면 그 멤버를 유지하는 `owner`가 살아 있어야 합니다. 반대로 외부 원본을 가리키는 참조 멤버를 반환했다면 외부 원본의 수명을 확인합니다. 참조를 담았던 객체의 수명을 무조건 따라가는 규칙은 없습니다.

원본이 동적 배열의 원소라면 소유 객체가 남아 있어도 재할당 등으로 원소 위치가 바뀔 수 있습니다. 다음 편에서 볼 vector의 원소 주소는 저장 공간이 유지되는 동안 사용해야 합니다. 포인터와 참조는 이런 변경을 자동으로 추적하지 않습니다.

지금까지는 접근의 유효 기간을 살펴봤습니다. 동적으로 확보한 원소를 누가 정리할지까지 객체가 맡으면, 복사와 이동을 설계하는 문제가 이어집니다. 다음 편에서는 그 책임을 소유권이라고 부르고 실제 배열로 확인합니다.
